# Local wheel control app

The user authorized building the app while away, in parallel with unattended
FFB debugging. The app should replace competing wheel-control processes and
provide Boxflat-like device settings and a clear web interface. Proceed with
local decisions; no unattended motor probes or game tests needing user feedback.

Use a Python standard-library HTTP server bound to 127.0.0.1:8765 and static
HTML/CSS/JavaScript. No cloud account, frontend build toolchain, or CDN. One app
owns its relay subprocess and serial connection. Monitor input passively.
Hardware setting writes happen only through an explicit Apply action. Saved
profile values and confirmed hardware readings must not be confused.

API contract (JSON; failed requests use {error: message}):
- GET /api/state: {device:{connected,name,path,axes:[{code,label,raw,min,max,value}],buttons:[{code,label,pressed}],effects:[string],slots},relay:{running,pid,profile,log:[string]},hardware:{connected,port,conflict,error,values:{}},profiles:[{id,name,game_id,settings:{}}],active_profile:string|null,games:[{id,name,abbr,status,detail,launch_options,input_status,ffb_status}],diagnostics:{items:[{label,status,detail}]}}
- GET /api/schema: {groups:[{id,label}],settings:[{id,label,group,description,type,min,max,step,unit,choices:[{value,label}]}]}
- POST /api/profiles {id?,name,game_id?,settings:{}} -> saved profile
- DELETE /api/profiles/ID -> {ok:true}; POST /api/profiles/ID/activate -> {ok:true} selects saved profile only, no device writes.
- POST /api/hardware/connect {} -> hardware status; POST /api/hardware/disconnect {} -> hardware status
- POST /api/hardware/apply {settings:{id:value}} -> {applied:{},errors:{},values:{}}; values are confirmed readings, do not fabricate success.
- POST /api/relay/start {profile:'native'|'compact',name?,product?}; POST /api/relay/stop {} -> relay status.
- GET /api/diagnostics/export downloads a bounded JSON report, no whole environment or secrets.
- Mutations require X-Mozaproxy-Token from GET /api/session {token}; reject hostile Origin/Host and non-JSON requests. Static server must prevent traversal.

Hardware integration interface: mozaproxy.hardware.HardwareController with
status(), connect(), disconnect(), apply(settings), close(); module schema()
returns above schema. Optional pyserial. Hardware errors are returned visibly;
server remains usable when wheel, serial access, or optional dependencies absent.

Design: desktop wheel tuning at a dim sim rig; graphite sidebar, warm off-white
work surface, restrained burnt-orange active indicators, fine separator rules,
clear unit-bearing settings rows, large accurate steering dial and pedal travel
bars. Six routes: Overview, Wheelbase, Pedals & controls, Profiles, Games,
Diagnostics. Exact data; no fake telemetry. Unsupported device operations are
clearly unavailable, never inert controls masquerading as functional ones.

Compatibility truth: FH5 confirmed driving/FFB with compact R9 + isolation,
freezes unresolved. JDM inputs/paddles work through direct HID, FFB experimental
and incorrect, freezes persist even helper removed and GE11 runtime. FS22/25,
AC/ACC require tests. Native AC/ACC operation should not start a proxy.
